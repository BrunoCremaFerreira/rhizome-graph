Scope: the graph answers **where** an agent is working and never **why**. `TodoWrite` is the tool
by which an agent writes down its own plan and marks one item `in_progress`; capturing it and
painting that one item under the agent's figure is the cheapest line of text that answers *why*.
One matcher, one derived string, one field on a frame the sibling plan also uses, one more sprite
per actor.

**This is not a small feature because the text is short.** It is the first thing in this program
that takes a string a language model wrote and rasterises it, and section 2 spends most of its
length on that. Everything else about it is genuinely cheap.

**The backend suite could not be run here and no number is invented for it.**
`.venv/bin/pytest` does not exist, `.venv/bin/python -m pytest` answers `No module named pytest`,
and the system `python3` has none. Installing one is forbidden by this agent's rules and by the
project's. The static count is a floor, not the suite's number -- `CLAUDE.md` records
`1498 passed, 20 skipped`, and the gap is parametrised cases a `grep` cannot see. **Every claim
here about backend behaviour comes from reading the source, never from a green run**, and section
7 says so again.

Four of these decide the design, and the last one decides most of it.

- **A hook invocation costs 40.6 ms and 20.1 ms of it is the interpreter starting.** The work
  inside is 0.061 ms. So a matcher's price is one more Python process on the agent's loop per
  firing. `TodoWrite` differs from the sibling plan's three matchers in exactly this: its firing
  rate scales with the **agent's** work, not with a human's. That is R11, and it is the one cost
  in this feature that no dedupe can remove.
- **The whole todo list is 1 337 bytes and the derived caption is a few dozen.** A 25x difference,
  re-sent on every `TodoWrite`. That alone would not decide it -- decision 3 does -- but it is the
  arithmetic behind it.
- **The frame is 174 bytes per agent, deduped.** There is no wire cost to argue about, and saying
  so is what keeps attention on the one place that does cost.
- **`makeLabelTexture` sizes its canvas from `ctx.measureText`, and the caller's string is
  unbounded** (`renderer.ts:1516-1522`):

  ```
  const metrics = ctx.measureText(text);
  const pad = Math.max(2, Math.round(font * 0.25));
  canvas.width = Math.ceil(metrics.width) + pad * 2;
  ```

  **There is no `Math.min` anywhere on that line.** A 4 000-character caption at 2x DPR asks for a
  52 012 px wide canvas, and at 3x DPR for 78 020 px. That is past the maximum canvas dimension of
  every browser engine, and far past a typical WebGL `MAX_TEXTURE_SIZE` of 4 096 to 16 384 -- so
  the texture is rejected or silently clamped, and 7.5 to 17.5 MiB is allocated per repaint on the
  way there. **Today no caller can reach it**: file names come from paths, and the actor caption
  is capped at `MAX_ACTOR_LABEL_CHARS = 24` (`labels.ts:264`) by `actorDisplayName`. This feature
  is the first caller that would hand it a string somebody else wrote. **The arithmetic above is
  computed from the source, not observed in a browser** -- this host has none -- but the absence
  of the `Math.min` is a fact about the file, and it is why R8 is a step of its own.

## 1. Assessment: how text reaches the screen today

### The seams, and which are load-bearing

**The hook forwards the payload untouched and classifies nothing**
(`rhizome_graph/hook.py:55-66`). `_forward` traces, parses the envelope, checks it is a `dict`,
and sends. It never reads `tool_name` or `tool_input`. **Adding `TodoWrite` to the matcher
therefore requires no change to the hook at all** -- the stdlib-only rule and the never-fail-loudly
rule are not approached, and the 1 482-byte payload costs the same 0.061 ms socket write as a
200-byte one. **Load-bearing, unchanged.**

**`normalize._resolve_operation` returns `None` for every tool it does not know**
(`normalize.py:243-244`), so a `TodoWrite` payload arriving today produces no event and no error.
The capture is additive by construction. **Load-bearing: it is why R4 cannot break anything that
exists.**

**`hookinstall.CAPTURED_TOOLS` is one tuple that three things read** (`hookinstall.py:70`):
`HOOK_MATCHER` joins it (`:73`), `hook_block` writes it (`:167-180`), and
`tests/test_hook_install_model.py:739-755` asserts the written block covers at least what
`config/settings.json` covers. And `tests/test_capture_settings.py:89-95` asserts
`REQUIRED_TOOLS <= covered` with a docstring saying in as many words that "adding a sixth tool is
not a regression and must not fail this" (`:13-16`). **Load-bearing: adding a matcher is
non-breaking by the tests' own design, and no existing assertion has to move.**

**`set_status` is the replaceable-slot pattern** (`server.py:252-269`): a dedupe on the encoded
message rather than on the dict, "because that is exactly what a client would receive", one line
in `replay_messages` (`:221`), one clause in `reset` (`:301`). A caption is a standing fact with
exactly that lifetime. **Load-bearing, copied exactly.**

**`ensureActor` already owns a caption sprite, in `overlayScene`, repainted only on change.**
`renderer.ts:1249-1252` builds it from `actorDisplayName(label, agent)`; `renameActor`
(`:1277-1289`) replaces the texture only when a *better* caption arrives, because "repainting
costs a canvas and a texture upload"; `updateLabels` places it every frame at
`actor.y + AVATAR_WORLD_HEIGHT + metrics.offset` (`:1347-1349`); `disposeSprite` releases it on
`resetScene` (`:751-757`). **This is the whole of the machinery this feature needs, already
built, already tested at its pure edges. Load-bearing, and decision 5 is mostly a matter of
noticing it.**

**`overlayScene` is drawn after the composer with `autoClear = false`**, which is the "text is not
part of the glow" doctrine (`CLAUDE.md`, and `renderer.ts:259` records that "every glyph pixel is
above the bloom's threshold"). A second sprite added to the same scene inherits it **by
construction**, with no new argument to make. **Load-bearing, and it is the strongest single
argument for decision 5.**

**`textContent`, never `innerHTML`, everywhere in the HUD.** Fourteen painters and not one
`innerHTML` in `web/src/`; `fileViewHud.ts:15` states the rule explicitly for the case that is
already arbitrary content -- "the body is an arbitrary file". **Load-bearing as a precedent, and
decision 5 makes it moot here rather than relying on it.**

**`actorDisplayName` is the existing "text from the network, bounded before it is drawn" rule**
(`labels.ts:299-305`): trim, fall back, cap at `MAX_ACTOR_LABEL_CHARS = 24`, **keep the head**
because "it is the part that identifies which agent this is". Its docstring adds "never throws: a
stale client or a future daemon may send anything". `label` -- which comes from the payload's
`agent_type` -- has always been model-adjacent text, and this is the function that has been
protecting the canvas from it. **Load-bearing, and the model R6 copies.**

### The six things that are actually in the way

1. **Nothing reads `tool_input` for anything but a path.** `normalize.py` asks
   `tool_input.get("file_path")` (`:251`) and `tool_input.get("command")` (`:329`) and nothing
   else. There is no function anywhere that takes a payload and answers with a *sentence*.
2. **`makeLabelTexture` has no width bound** (`renderer.ts:1519-1522`, and section 0). The
   existing callers are safe by accident of their inputs, not by a check. This feature is the
   first that would hand it text a model wrote.
3. **There is no per-agent slot in the hub.** `EventHub` holds `_known_paths`, `_seed`,
   `_recent`, `_meta`, `_status`, `_reset`, `_last_hook`, `_hook_paths`, `_fs_paths`
   (`server.py:189-203`). Nothing is keyed by agent. **This obstacle is shared with the sibling
   plan and is solved once**, see R3.
4. **The 48-sprite file-label pool is bound to paths and gated on zoom.** `MAX_FILE_LABELS = 48`
   (`labels.ts:41`) is the pool size, `selectFileLabels` chooses by heat and by
   `FILE_LABEL_ZOOM_THRESHOLD = 90` (`:28`), and the renderer keeps a slot bound to a path so "a
   new event does not repaint every canvas" (`CLAUDE.md`). An agent caption is bound to an
   **agent**, must be visible at every zoom, and must not compete for a slot with 48 hot files.
   Sharing that pool is the obvious reuse and it is wrong; decision 5 says so with its reasons.
5. **`Actor` carries no text at all.** `{agent, intensity}` (`simulation.ts:46-53`); the label
   lives on the renderer's `ActorView` (`renderer.ts:91-102`), which has no unit test by
   doctrine. There is no pure module between the socket and the figure. **Shared obstacle**, see
   R7.
6. **`ingest_line` stamps the active agent from any payload carrying one** (`server.py:340-342`).
   A `TodoWrite` **is** a tool call, so unlike the sibling plan's three events it *should* stamp
   it -- an agent updating its plan is genuinely at work. Listed here so that nobody "fixes" it
   in this direction: R1 of the sibling plan narrows the stamp to payloads carrying a
   `tool_name`, and `TodoWrite` carries one, so the two plans agree without either of them
   having to know about the other.

### One defect this feature exposes rather than creates

- **`makeLabelTexture` is unbounded, and it is the sink for every piece of text on the graph.**
  Obstacle 2. Pre-existing and unreachable today; this feature is what makes it reachable. The
  fix belongs in `makeLabelTexture` itself rather than in the caption path, because a bound that
  only the caption honours is a bound the next caller will not. R8, **now**, and it is the one
  step here that would be worth taking even if the rest of the feature were dropped.

## 2. Decisions before step 1

Decisions 1-3 follow from the assessment. Decisions 4-13 are mine; say so if you would have
chosen otherwise. Three of them (3, 5, 8) are places where I did **not** ratify the brief this
plan was commissioned from.

**1. Step 0 is the sibling plan's measurement step, run once.** `CLAUDE.md`'s "Agent attribution"
section is the standard: the `PostToolUse` shape "was settled by capture, not by reasoning --
measured against Claude Code 2.1.229 with `RHIZOME_TRACE_LOG`". Nothing here has ever seen a
`TodoWrite` payload. **This plan defines no measurement of its own**; it adds two questions to
the one in `2026-08-26-20-56-agent-lifecycle-events.md`, step 0, and every field named below is an
assumption until that trace replaces it.

**2. The assumed shape, stated so a surprise is visible.** `tool_input.todos` is a list of
objects, each with `content` (the imperative form), `status` (one of `pending`, `in_progress`,
`completed`) and `activeForm` (the present-continuous form). **`activeForm` is the field to
paint** -- it is the one Claude Code asks the model to write in the form a reader wants under a
figure. `content` is the fallback. If step 0 finds no `activeForm`, the feature still works off
`content` and the caption reads as an instruction rather than as an activity; that is a
degradation, not a blocker.

**3. The daemon sends the derived caption, never the list.** Rejected: shipping `todos` and
letting the browser choose. Two reasons, and the second is the real one. The wire arithmetic is
1 337 bytes against a few dozen, re-sent on every `TodoWrite` (section 0) -- worth having but not
decisive. **The decisive one is that "which item is in progress" would then have two
implementations**, and the browser's would be the one running against a list it also has to
validate item by item. This program has a name for that mistake: `content_search.py`'s result
frame "carries `[{path, count}]` and nothing else -- no lines, no columns, no preview", precisely
so the browser is not a second definition of where the matches are. Same rule, one feature
smaller. **The stated price: the browser cannot show the *rest* of the plan -- how many items are
done, what comes next -- without a second round trip. R12 records that with its trigger.**

**4. One frame, `kind: "agentState"`, shared with the sibling plan.** `caption` is a field on the
per-agent entry, beside `state`. See "How the two plans compose". A second per-agent frame kind
would mean two dedupe slots, two replay lines, two `reset` clauses, two parsers and two routes,
all answering questions about the same actor.

**5. The sink is a SPRITE in `overlayScene`, a second line under the actor's name.** The brief
asks for the trade against the "text is not part of the glow" doctrine and against a figure that
moves every frame. Four candidates, and three of them lose:

- *A DOM element.* Every other piece of text that follows a world position on this page is a
  sprite, and the reason is mechanical: the figure moves every frame (the force layout never
  settles) and the camera moves independently, so a DOM caption means projecting world to screen
  and writing `style.transform` **per agent, per frame**. That write has to come from
  `renderer.ts` -- the one module with no unit test by doctrine -- through a new seam that hands
  screen coordinates out of it. It also buys nothing: DOM text would be crisper only if the
  sprite path were blurry, and `labels.ts` spends four rules (`spriteHeightForEm`,
  `labelFontPixels`, `snapToPixelGrid`, `SRGBColorSpace`) making it not blurry.
  **Rejected on the seam, not on the pixels.**
- *The 48-sprite file-label pool.* Obstacle 4: its slots are bound to **paths**, its selection is
  by heat and zoom (`selectFileLabels`, `FILE_LABEL_ZOOM_THRESHOLD = 90`), and its cap exists to
  stop a burst of writes becoming hundreds of draw calls. An agent caption would compete with
  file names for those 48 slots and disappear whenever 48 files were hot -- which is exactly when
  the user most wants to know what the agent thinks it is doing. **Rejected.**
- *`avatar.ts`.* It paints a figure into a 64 px square with `AVATAR_SIZE` coordinates and no
  text (`avatar.ts:45-82`), and its sprite lives in **`this.scene`** (`renderer.ts:1244`), which
  is the bloomed one. Text there gets the additive halo that "closes the counters of its letters"
  -- the exact failure `CLAUDE.md` records. It would also mean re-rasterising the figure on every
  caption change. **Rejected, and it is the candidate that would violate the doctrine the brief
  names.**
- *A second sprite of the kind the actor already has.* `ensureActor` builds one
  (`renderer.ts:1249-1252`), `renameActor` repaints it only on change (`:1277-1289`),
  `updateLabels` places it every frame (`:1347-1349`), `disposeSprite` frees it (`:756`), and it
  is in `overlayScene`, so it is outside the bloom **by construction**. Per frame it costs one
  more `placeLabel`; per *change* it costs one canvas and one texture upload, which is what the
  existing caption already costs and which a `TodoWrite` triggers at most a few dozen times a
  session. **Chosen.**

**6. The caption is smaller than the name, and capped harder.** `LABEL_PIXEL_HEIGHT = 13`
(`labels.ts:22`) is the name's on-screen height; the caption takes a fraction of it. It is
secondary information under a primary identifier, and a caption drawn at the same weight as the
agent's own name competes with the thing that says *who*. **This is a judgement about a screen
nobody here can see** -- section 5.

**7. The cap is enforced on BOTH sides, and that is two conditions on one path, not two paths.**
`CLAUDE.md`: "Depth of defence here means two conditions on one path, never two paths." The
daemon caps so the wire is bounded and so a browser from another version is protected; the
browser caps so a **daemon** from another version, or one nobody in this repository wrote, cannot
reach the canvas. The path is the same one -- payload to sprite -- and it passes two checks.
Neither is a second route to the sink.

**8. The character cap does not bound the canvas, so there are two different caps.** This is the
decision I most expect to be argued with, so here is the arithmetic. A cap in **code points**
does not bound rasterised width: 40 full-width CJK glyphs at 26 px are roughly twice the pixels of
40 Latin ones, and a string of combining marks is narrower than either. `makeLabelTexture` sizes
its canvas from `ctx.measureText(text).width` (`renderer.ts:1517-1521`) with **no `Math.min`**.
So:

- **`MAX_CAPTION_CHARS`** (decision 9) bounds the wire and the model. Pure, testable, in both
  languages.
- **`MAX_LABEL_TEXTURE_PX`** bounds the canvas, unconditionally, **in `makeLabelTexture` itself**
  -- one `Math.min` that protects every label on the page, not just this one. Text past it is
  clipped, which is a visible and harmless degradation.

A measure-and-retry truncation loop would be the alternative and it is worse: a loop over
untrusted input, in the untestable module, to compute what one `Math.min` bounds outright.

**9. `MAX_CAPTION_CHARS` is 60, head-kept, with the existing ellipsis.** 60 rather than
`MAX_ACTOR_LABEL_CHARS`'s 24, because a caption is a clause and 24 characters cuts most of them
mid-verb; 60 rather than 200, because at 26 px a 60-character caption is already ~800 px of
rasterised width, which at the graph's usual zoom is a bar across a good part of the screen.
**Head-kept, not `truncateMiddle`** (`protocol.ts:595`): that helper exists for **paths**, where
both ends carry information. In a clause the head is the verb and its object, which is the whole
of what the caption is for -- the same reasoning `actorDisplayName` records for the agent's name
(`labels.ts:303`).

**10. The fold strips control characters, bidirectional controls, and collapses whitespace --
in that order, in a pure function, in both languages.** Each has a named reason:

- **C0 and C1 controls, `\n` and `\t` included.** `ctx.fillText` does not break lines: a `\n` is
  handed to the platform shaper and comes out as a missing glyph box or as nothing, depending on
  the platform, and either way the caption silently stops being one line of legible text. A
  caption is one line by construction, so a newline is not a formatting request, it is noise.
- **U+200E, U+200F, U+202A-U+202E and U+2066-U+2069** -- the bidirectional marks, embeddings,
  overrides and isolates. `ctx.fillText` runs the platform's bidi algorithm, so a
  RIGHT-TO-LEFT OVERRIDE inside a caption reverses the visual order of what follows it. **The
  caption sits directly under the agent's name**, which is the one string on this page a user
  trusts to say who is acting; text that can reorder itself around that name is a small but real
  spoofing surface. The blast radius is a graph, not a credential -- which is why this is a fold
  rule rather than an alarm -- but it costs one character class to remove and there is no case
  for keeping it.
- **Collapse runs of whitespace to single spaces, then strip.** After the two removals above a
  caption can be mostly spaces, and a 60-character cap on a string of spaces is a wide empty
  texture.

**Deliberately NOT done: no HTML escaping and no quoting.** The sink is a canvas, not the DOM
(decision 5), and `fillText` cannot execute markup. Escaping it would be a defence against a sink
this feature does not have, and defences against absent sinks are how a reader concludes the real
sink was thought about. **If anyone later routes the caption to a DOM element, `textContent` is
the rule** (`fileViewHud.ts:15`) and this paragraph is the reason it has to be restated.

**11. No in-progress item means an empty caption, not a fabricated one.** Not "idle", not the
last completed item, not the first pending one. An empty caption hides the sprite and the figure
keeps its name. Inventing text is how a graph starts lying quietly: "idle" would be indexed by a
reader as a fact about the agent, when what actually happened is that the model did not mark
anything. **An absence is a legitimate answer** -- the same rule `_parse_bash` follows when it
"would have to guess" (`normalize.py:316-327`), and the same one `statusList` follows by not
drawing a permanent empty strip.

**12. Two agents sharing one todo list show the same caption, and that is truthful.** The caption
is keyed on the **actor**, never on the list -- `agent` is identity (`CLAUDE.md`, twice). If a
subagent writes to a list the orchestrator also writes to, each figure carries the caption derived
from **its own** `TodoWrite` payload, at the time that payload arrived. Two figures reading the
same sentence is a correct statement that they are working from one plan. **The stated price: a
subagent that never calls `TodoWrite` carries no caption at all, even while the orchestrator's
list describes what it was asked to do.** That is also correct, and it is the direction to fail
in -- the graph says what it observed, not what it inferred.

**13. `reset` clears every caption.** The same clause as `_status`'s (`server.py:301`) and for a
sharper reason than usual: a caption describes work in a project the user has left, under a figure
that describes an agent of that project, and nothing on screen would say so.

### How the two plans compose

`2026-08-26-20-56-agent-lifecycle-events.md` was written at the same time and **shares two things
with this one**. Neither plan may be built in a way that forces the other to rework. This section

- **Step 0 is one measurement, not two.** Both plans need a `RHIZOME_TRACE_LOG` capture from a

- **`rhizome_graph/agentstate.py` is the module name in both.** One module answers "what does this
  payload say about this agent", whichever half of it lands first.
- **`web/src/agentState.ts` is the browser-side model in both**, and this plan adds
  `web/src/agentCaption.ts` beside it for the fold and the cap, which are this feature's alone.

### Step 0 -- Nobody here has ever seen a `TodoWrite` payload. **Rank: now, and nothing may precede it**

**What is missing.** Facts, not code. Decision 2 states an assumed `tool_input` shape and the
whole of R1 is built on it.

**Where it is defined.** `2026-08-26-20-56-agent-lifecycle-events.md`, step 0. **Do not write a
second measurement step.** That one already installs a widened `PostToolUse` matcher with a
`RHIZOME_TRACE_LOG` prefix on a scratch project and runs one real session; adding `TodoWrite` to
the same matcher costs nothing and captures both plans' payloads in one file.

**The two questions this plan adds to it.**

| # | Question | Which step depends on it |
|---|---|---|
| 0.9 | Does `tool_input.todos` exist, is it a list of objects, and do those objects carry `content`, `status` and `activeForm`? What are the exact `status` values? | R1, all of it |
| 0.10 | Does a **subagent's** `TodoWrite` carry `agent_id`, so its caption lands on its own figure rather than the session's? And does a subagent call `TodoWrite` at all? | Decision 12, and R11's cost estimate |

**What happens on a bad answer.** 0.9 partially negative (no `activeForm`) degrades the caption to
`content` and the feature still ships -- decision 2. 0.9 wholly negative (no `todos`, or a shape
nothing can be derived from) retires the feature, and **R8 should still be built**, because the

### R2 -- The derived string is unbounded and carries whatever the model typed. **Rank: now**

**What is wrong.** `caption_of` returns a substring of a payload field. A `content` is written by
a language model and is bounded by nothing this program controls; it may hold newlines, tabs, C0
controls, and bidirectional overrides. **It is a step of its own rather than three lines inside
R1** because it is the security surface of this feature and it should be reviewable, and
testable, without reading the derivation beside it.

**Where.** `rhizome_graph/agentstate.py`, a second pure function, applied by the hub in R3 and
**not** by `caption_of` itself.

**Why it costs.** Three distinct costs, in descending order of certainty:

- **The wire.** Uncapped, one caption is whatever the model wrote -- a paragraph is a few
  kilobytes, in a frame republished on every `TodoWrite` and replayed to every connecting client.
  Small in absolute terms; unbounded is the problem, not the size.
- **The canvas.** Section 0's arithmetic: a 4 000-character caption asks `makeLabelTexture` for a
  52 012 px wide canvas at 2x DPR and 78 020 px at 3x, past every browser's maximum dimension and
  past a typical WebGL `MAX_TEXTURE_SIZE`, allocating 7.5 to 17.5 MiB on the way. **R8 is the
  unconditional bound and this cap is the first of the two conditions** (decision 7).
- **The line.** A newline in `fillText` is not a line break; it is a missing-glyph box or nothing,
  and the caption stops being legible with no error anywhere (decision 10).

**Target shape.**

```
MAX_CAPTION_CHARS = 60

safe_caption(text: str) -> str     # fold, then cap, head kept
```

The order is fixed and each stage has a reason (decision 10): strip C0/C1 controls, strip the
bidi controls and isolates, collapse whitespace runs, strip the ends, **then** cap at
`MAX_CAPTION_CHARS` keeping the head with the ellipsis `labels.ts` already uses. Capping before
folding would count characters that are about to be removed and produce a caption shorter than the
cap for no reason.

**The boundary afterwards, and what stops it being crossed.** `safe_caption` is the only way a
caption enters the frame, and R3 step 3.3 asserts that the hub calls it -- so a future caller that
puts `caption_of`'s output straight onto the frame fails a test rather than shipping. **The
browser applies the same rule again** (R6), because this daemon is not the only thing that could
ever send an `agentState` frame.

### R10 -- A caption outlives the work it describes. **Rank: next**

**What is wrong.** A `TodoWrite` marks an item in progress; the agent finishes the whole plan and
its last `TodoWrite` marks everything `completed`, so R3 step 3.5 publishes `caption: ""` and the
sprite hides. **That is the well-behaved path.** The badly-behaved one is common: the model
finishes without a final `TodoWrite`, or the session ends, and the last caption stands under a
figure forever -- describing work that finished an hour ago, with nothing on screen saying so.

**Why it is `next` rather than `now`.** The answer already exists in the sibling plan and costs
nothing extra: `state` on the same entry goes `stopped` on `Stop`/`SubagentStop`, and a caption is
simply not drawn for a stopped agent. Building a **second** staleness mechanism here -- a
timestamp cut on the caption alone -- would be two rules about the same figure, and the sibling
plan's decision 9 already puts one of them in `agentState.ts` where it is testable.

**Trigger to promote it to `now`:** the sibling plan is not going to be built. Then the caption
needs its own rule, and the shape is the sibling plan's: the entry carries `ts`, the browser
decides staleness from a `now` it is passed, and `captionFor(state, agent, now)` answers `""` past
the cut. Pure, one selector, one test -- **not** a timer in the daemon, for the reason that plan
states: a human can be away for an hour with the agent genuinely mid-item, so a timeout reports
false progress.

**Owner.** `developer-frontend`, if the trigger fires.

### R11 -- The hook cost cannot be deduped away. **Rank: noted**

**What is true.** R3's dedupe is on the **wire**: a `TodoWrite` that does not change which item is
in progress broadcasts nothing. The 40.6 ms Python process has already been spent by then, on the
agent's loop, before the daemon saw anything. **The only lever on that cost is the matcher
itself.**

**Why it is noted rather than a defect.** There is no cheaper place to be. The hook cannot filter
-- it forwards the envelope and classifies nothing (`hook.py:55-66`), and giving it a filter means
putting a `tool_input` parse on the hot path, which is the thing `CLAUDE.md` and
`tests/test_hook_dependencies.py` exist to prevent. A `PreToolUse` matcher would fire *more*
often, not less. Batching is not available: the hook is a process per call by construction.

**Trigger:** step 0's trace giving a real `TodoWrite` count for a session, and that count being
high enough that 40.6 ms x N is a number somebody notices. My estimate is 20-60 firings, so
0.8-2.4 s per session, spread in 40 ms pieces. **If the trace says 500, this feature's matcher
should be reconsidered rather than optimised**, because there would be no optimisation available
-- only the choice to capture or not.

### R12 -- The caption is one line of a plan the browser cannot see. **Rank: noted**

**What is missing.** Decision 3's stated price: the frame carries the derived caption and not the
list, so the page cannot show how many items are done, what comes next, or the shape of the plan.
A panel listing an agent's todos -- the way the bottom-right panel lists what is uncommitted --

**Why noted.** It would be a second frame or a much larger one, a panel with its own model and its

**Trigger:** somebody watching the window and wanting to know what comes next rather than what is
happening now. If it is built, it should ship the list on **request** -- a command kind, like
`sizes` -- rather than pushing it on every `TodoWrite`, so the 1 337 bytes cross the wire when
someone asks and not forty times a session.

### R13 -- The caption is invisible to search and to the recent-changes list. **Rank: noted**

`ctrl+F` matches file names and paths (`search.ts`); the content search matches file contents; the
recent-changes list holds `A`/`M`/`D` events (`eventLog.ts:82-90`). A caption is in none of them,
so "which agent was working on the parser" is not a question the page can answer.

**Why noted.** Both searches are about *files*, and their whole design -- `frameMatches` returning

**Trigger:** more than a handful of agents on screen at once often enough that finding one by what

## 4. What conflicts with what

- **Simplicity vs a second definition, at what crosses the socket.** Shipping `todos` is one less
  function in the daemon and one more in the browser, and it would let R12 be free. The rule that
  decides it is `content_search.py`'s: its frame "carries `[{path, count}]` and nothing else",
  because a browser that recomputes is a browser that can disagree. **One definition wins**, and
  the price -- R12 needs a round trip it would otherwise have had for nothing -- is stated rather
  than hidden.
- **Maintainability vs safety, at the two caps.** One cap in one place is the maintainable answer
  and it is not available: a character cap does not bound a canvas width, and a canvas bound does
  not bound the wire (decision 8). So there are two constants with a **test asserting they agree**
  (R8 step 8.3), which is the cheapest form of the coupling. The alternative -- one cap, in the
  renderer, on rasterised width -- would put the whole rule in the module that has no tests.
  **Safety wins, and the maintainability cost is one assertion.**
- **Performance vs completeness, at the matcher.** 40.6 ms per firing on the agent's loop, at a
  rate that scales with the agent's work rather than a human's (R11). **Completeness wins at my
  estimated 20-60 firings and would not win at 500**, and the trigger to revisit it is written
  into R11 rather than left as a feeling. This is the sharpest difference between this plan and
  the sibling one, whose three matchers all fire at human rates.
- **The doctrine vs the requirement, at the sink.** "Text is not part of the glow" says text goes
  in `overlayScene`, drawn after the composer. A caption that follows a figure moving every frame
  says the text must be positioned every frame from live world coordinates. Those two look like a
  conflict and are not: `overlayScene` sprites are already positioned every frame by
  `updateLabels` (`renderer.ts:1322-1352`), and the actor's name is already one of them
  (`:1347-1349`). **The apparent conflict is what the DOM candidate in decision 5 was reaching
  for, and it dissolves on reading the existing loop** -- which is why decision 5 is a paragraph
  of elimination rather than an invention.
- **Security, and where it actually is.** This feature adds **no inbound command**:
  `COMMAND_KINDS` (`server.py:464`) is untouched, so the two gates (`control_allowed` then
  `token_matches`, `:843-866`) gain no caller. It resolves no path, forks nothing, opens no file.
  **What it does is take free-form text written by a language model, broadcast it to every
  connected browser, and rasterise it.** That is one path with two conditions on it (R2 in the
  daemon, R6 in the browser) and one unconditional bound at the sink (R8). The sink is a canvas,
  not the DOM, so there is no markup question -- decision 10 says so explicitly rather than adding
  an escaping step against a sink this feature does not have. **`security-auditor` should read
  this plan and the sibling one as one change**, because the sibling plan declares the `caption`
  field and this one is what makes it free-form.

Nothing here adds a path around a chokepoint: `resolve_inside` stays the only containment check
and is not involved; `gitcmd` stays the only fork and is not involved; `WsClient.send` stays the
only token stamp and gains no caller, because nothing in this feature travels inbound; the two
gates stay in front of every command and the set of commands is unchanged.

## Consultation: `security-auditor` (2026-08-26)

Appended by the orchestrator. The audit covered all five plans of this batch **together** and
ranked one critical, five high and seven medium findings; the full report is
`docs/security/2026-08-26-audit-five-planned-features.md` and it is the authority. This section is a pointer into it, never a second
copy of it. It was written against the feature descriptions, **not** against this document --
the auditor states so itself -- so where the two disagree the disagreement is real and unresolved,
not an editing slip.

### Findings that land on this plan

- **C1 (critical).** The in-progress todo item is the agent's plan in prose -- ticket numbers, customer names, the
  sentence a user typed. The broadcast side asks for **nothing** (probed: a client with no token
  received the full replay) and `start.sh` binds every interface, so anyone who can reach `:8080`

  per-actor **slot**, never an `Event` and never in `_recent` (or it is replayed to a client that

- **H2 (high).** `makeLabelTexture` sets `canvas.width` from the text's own measured width with **no**
  `Math.min` (`renderer.ts:1519-1522`); the existing 24-character cap lives in `actorDisplayName`
  and a new caption inherits nothing from it. A 4 000-character todo -- which a model does write --
  asks for a canvas past every engine's dimension limit. Caps: displayed characters, 256 bytes on
  the wire, C0/C1 folded to a space **before** the cut, bidi overrides stripped.
- **H3 (high).** See the lifecycle plan: the group-writable ingest socket means one forged line puts arbitrary
  text under any agent's figure, and onto the LAN broadcast.
- **M1 (medium).** The caption frame must be routed above `parseEvent`, which ignores `kind` entirely.
- **M2 (medium).** Adding `TodoWrite` to `HOOK_MATCHER` leaves a user who hand-copied the old block with no
  caption and a `--doctor` that says `installed`. Worth one line in the plan.
- **M5 (medium).** One pure `sanitizeDisplayText`, shared with the notification builder and the event rows.
- **M7 (medium).** The accidental 64 KiB ingest cap bounds what a caption payload can carry.

### The auditor's own summary of this feature

**2. TodoWrite caption -- the highest-severity single finding.** New untrusted input: arbitrary
model-authored prose, on the socket, on the broadcast, into a canvas. The DOM is safe by
existing practice (`textContent` everywhere, no `innerHTML` in `web/src/`, verified) but that
practice is unpinned; the canvas is unsafe by length, not by markup. The token is irrelevant
again, and here that is the finding: the broadcast has no gate at all and binds every interface
under `start.sh` (C1). Caps: 64 displayed characters, 256 bytes on the wire, controls folded,
bidi stripped. The caption is a per-actor slot, never an `Event`, never in `_recent`.
